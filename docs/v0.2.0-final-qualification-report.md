## Shared sensitive-data boundary

### Root cause

The original URL scan stopped at any whitespace inside an apparent authority. Percent and form decoding, and Unicode normalization, could introduce such a boundary before the userinfo delimiter. The scanner had no way to distinguish an incomplete authority from ordinary text. Query authorization and display redaction applied different whitespace treatments, so neither the later parser nor redaction reliably recovered that security decision.

On the 380-test baseline, synthetic userinfo followed by a space or a nonbreaking space before its delimiter returned `allowed` in otherwise nonsensitive nested query values. Percent-encoded values retained the synthetic credential marker through `redact_text`, default `redact_url`, and nested `redact_structure`. Form-encoded space also passed authorization and retained the marker in the URL and structure output. These probes used an isolated, synthetic policy and made no network requests.

### Design and compatibility

All sensitive URL authority consumers now use a shared `CLEAN`, `SENSITIVE`, or `AMBIGUOUS` decision. The inspector examines the source and at most four percent/form-decoded views. The views use NFKC and limited structural escapes for URL punctuation, whitespace, and controls. The primary scan checks the apparent authority, including malformed boundaries. A compact inspection-only view looks for userinfo obscured by Unicode whitespace or control characters. A match that only becomes visible across such a boundary is sufficient to deny or mask the input, without inferring its intended meaning.

A positive sensitive decision produces `sensitive_url` where normal URL validation has established the outer URL. A malformed, unsupported, or ambiguous decision produces `invalid_url`. Both stop before DNS and HTTP. Inspection views cannot supply an outbound destination, path, or query. The existing canonical form and policy fingerprint checks still govern the actual request. Display code removes clear literal userinfo selectively where possible and suppresses the entire affected value or query when it lacks reliable boundaries. This also applies to keys and values in diagnostic structures, audit records, and artifact metadata.

Supported benign input includes normal prose, encoded nested URLs with clear authorities, standard form values, repeated keys, percent-encoded Unicode text, and escaped punctuation. The engine now rejects apparent whitespace-split or malformed nested authorities even without detectable userinfo. Encoded control and format characters can also make query values ambiguous. Put explanatory prose in a separate query parameter when a nested URL value would otherwise combine it with its authority.

Query inspection stays at 4,096 characters and four decoding steps. Display text inspection is capped at 65,536 characters, and structured redaction has depth and item bounds. Malformed encoding, excess input, and undecidable nested authority syntax fail conservatively. The scanner does not establish safety for arbitrary application-specific encodings, encrypted data, or plaintext secrets outside recognizable patterns. Raw evidence is outside this redaction guarantee.

## TLS interoperability

The fixture generated an ECDSA test CA and a CA-signed leaf with SAN `tls.example.test`. A Python TLS server bound to one ephemeral port on `127.0.0.1`. The harness substituted fixture DNS and admitted only that loopback IP in the test's address classifier, while a socket guard limited TCP to the exact port. Trusted cases used the temporary CA in the test context. The test observer called the real OpenSSL handshake and captured any verification error before dependency error translation.

| Scenario | Result |
| --- | --- |
| Trusted CA and matching SAN | Real handshake and HTTP response succeeded. SNI was `tls.example.test`, and HTTP Host retained the hostname and test port. The server observed EOF after the response closed. |
| Certificate issued by an untrusted CA | OpenSSL reported an issuer verification failure. No HTTP request was received. |
| Trusted CA and wrong hostname | OpenSSL reported a hostname mismatch. No HTTP request was received. |

The fixture exercises the shared policy and request path, numeric connection and peer checks, TLS context, HTTP/1.1, and cleanup. Production address checks and certificate verification remain in force. The isolated result does not establish routing or interception guarantees for external infrastructure. Native Burp runtime parity and Windows execution remain unverified.
