Fetch only each exact `download_url`, verify its filename, size and SHA-256 against the inventory, and compare the corresponding upstream `metadata_url` record. The following command creates a direct-reference download lock so pip can acquire the recorded wheel URLs without querying a package index or resolving extra dependencies. Set `candidate` to the verified source directory, `acquisition` to an existing new scratch directory, and `acquisition_python` to a local CPython 3.15.2 executable with pip available. Run on the qualified platform, then compare the downloaded filenames and their hashes with the recorded inventory before installing.

```bash
set -eu
provenance="$candidate/release/fedora45-cpython315-wheel-provenance.json"
mkdir -- "$acquisition/wheels"
/usr/bin/python3.15 -I -B - "$provenance" > "$acquisition/wheel-urls.txt" <<'PY'
import json
import sys
from pathlib import Path
from urllib.parse import urlsplit

for wheel in json.loads(Path(sys.argv[1]).read_text())["packages"]:
    url = urlsplit(wheel["download_url"])
    assert url.scheme == "https" and url.netloc == "files.pythonhosted.org"
    assert url.path.rsplit("/", 1)[-1] == wheel["filename"]
    print(f'{wheel["name"]} @ {wheel["download_url"]} --hash=sha256:{wheel["sha256"]}')
PY
env PIP_CONFIG_FILE=/dev/null "$acquisition_python" -I -B -m pip --isolated --disable-pip-version-check \
  --no-input download --no-index --no-deps --only-binary=:all: --require-hashes --no-cache-dir \
  --dest "$acquisition/wheels" -r "$acquisition/wheel-urls.txt"
```


`scope.py`, `campaigns.py`, and `notes.py` derive the project root from the resolved module file. Comparison also binds to `config/policies` there. Changing only the client working directory or switching `current` to another source tree changes or fails to move the policy and campaign paths. Keep `runtime`, its managed code, and the state directories physical. The release venv supplies dependencies, and the imports come from `runtime`. Installing the project itself into the venv would risk anchoring its defaults to site-packages. The source archive contains only public repository files, and upgrades copy only code.

The launcher checks ownership, restrictive directory permissions, the selected release identity, and the source and venv inventory before starting Python. It compares the active code against the sealed source and holds a shared lock for the server's lifetime. Activation acquires the exclusive lock, so it refuses while a cooperating server is running. The previous managed source entries are moved to a private `.retired-code-*` directory for recovery. Review and remove those code-only stashes after a successful cutover when they are no longer needed. If an activation is interrupted and the active code and selector disagree, launch fails. Rerun `activate` with a known sealed version and its recorded digest. Keep the trusted archive digest and the locally printed manifest digest in deployment records outside the launcher directory. Sealing records a locally verified deployment. Trust in the archive, wheelhouse, system interpreter, and installing Unix account comes from the operator's verification and permissions.

The venv uses `--copies` so Python entry points are physical. Fedora's venv `lib64 -> lib` alias is permitted only at that fixed venv location. Policy and campaign symlink restrictions still apply. The launcher guards cooperating clients and the managed code inventory. Keep direct `server.py` launches and other writers out of the stable tree. Verify this deployment again after a Fedora interpreter, system-library, or trust-store update.

## Fedora installation

These commands are for a reviewed future release bundle, after checking the source archive's SHA-256 and the wheelhouse's digest against trusted release metadata. Use a clean extraction directory. In the examples, `candidate` points to the verified extracted source archive and `wheelhouse` points to the verified directory of hash-locked binary wheels and requirement files. Use physical absolute paths. Run as the account that will own the stable installation.

```bash
set -eu
umask 077
root="$HOME/.local/share/recon-mcp"
candidate=/absolute/path/to/verified/recon-mcp-0.2.0
wheelhouse=/absolute/path/to/extracted/fedora45-cpython315
base=/usr/bin/python3.15
version=0.2.0
lock="$candidate/release/fedora45-cpython315-runtime.requirements.txt"

(cd -- "$wheelhouse" && sha256sum --check --strict SHA256SUMS)
cmp -- "$lock" "$wheelhouse/fedora45-cpython315-runtime.requirements.txt"
cmp -- "$candidate/release/fedora45-cpython315-wheel-provenance.json" \
  "$wheelhouse/fedora45-cpython315-wheel-provenance.json"

# Use these initial directory and launcher commands only for the first install.
mkdir -p -- "$HOME/.local/share"
mkdir -- "$root"
mkdir -- "$root/releases" "$root/runtime"
mkdir -- "$root/runtime/config" "$root/runtime/output"
install -m 0700 -- "$candidate/scripts/stable_deployment.py" "$root/stable_deployment.py"

release="$root/releases/$version"
mkdir -- "$release"
mkdir -- "$release/source"
cp -R -- "$candidate/recon" "$candidate/server.py" "$release/source/"
"$base" -I -S -B -c 'import platform, sys, sysconfig; assert sys.platform == "linux" and platform.machine() == "x86_64" and sys.version_info[:3] == (3, 15, 2) and sys._is_gil_enabled() and not sysconfig.get_config_var("Py_GIL_DISABLED"); print(sys.version)'
unshare --user --map-current-user --net -- "$base" -I -B -m venv --copies "$release/.venv"
py="$release/.venv/bin/python"
unshare --user --map-current-user --net -- env PIP_CONFIG_FILE=/dev/null \
  "$py" -I -B -m pip --isolated --disable-pip-version-check install \
  --no-index --no-deps --only-binary=:all: --require-hashes --no-compile \
  --find-links "$wheelhouse" -r "$lock"
unshare --user --map-current-user --net -- env PIP_CONFIG_FILE=/dev/null \
  "$py" -I -B -m pip --isolated --disable-pip-version-check check
"$py" -I -B - "$candidate/release/fedora45-cpython315-runtime.txt" <<'PY'
import importlib.metadata as metadata
import re
import sys
from pathlib import Path

def normalized(name):
    return re.sub(r"[-_.]+", "-", name).lower()

expected = {"pip": "26.3"}
for line in Path(sys.argv[1]).read_text().splitlines():
    if line.strip() and not line.startswith("#"):
        name, version = line.split("==")
        expected[normalized(name)] = version
actual = {}
for dist in metadata.distributions():
    name = normalized(dist.metadata["Name"])
    assert name not in actual and dist.read_text("direct_url.json") is None, name
    actual[name] = dist.version
assert actual == expected, (expected.items() - actual.items(), actual.items() - expected.items())
PY

(cd -- "$release/source" && "$py" -E -s -B -c \
  'import recon, server; assert recon.__version__ == "0.2.0"; assert len(server.AVAILABLE_TOOLS) == 67')
"$py" -E -s -B "$release/source/server.py" </dev/null
guard="$root/stable_deployment.py"
digest=$("$base" -I -S -B "$guard" seal "$root" "$version")
printf '%s %s\n' "$version" "$digest"
# Record the printed digest in your deployment record.
"$base" -I -S -B "$guard" activate "$root" "$version" "$digest"
"$base" -I -S -B "$guard" verify "$root"
"$base" -I -S -B "$guard" serve "$root" </dev/null
```

## Upgrade, migration, and rollback

1. Install and verify a new reviewed release under its own version directory. For an existing deployment, start the installation procedure at `release=...`. Keep the prior release, the recorded digests, and the previous configuration backup. Review any change to the launcher separately.
2. Stop clients and other writers using the stable tree before switching versions. Run `activate` with the selected version and its recorded manifest hash, then `verify`. Reconnect clients only after the disposable client checks pass.
3. From a development checkout or earlier installation, identify one authoritative campaign tree while all writers are stopped. Make a verified private backup if you intend to migrate it. Check owner, filesystem, permissions, symlink components, and source and destination locations before any move. Existing active and archived campaign roots and individual campaign directories require `0700` under the running account. A group-writable output parent fails the runtime check. A first deployment can start with empty state.
4. Migrate the authoritative `output` tree once. Prefer a reviewed same-filesystem rename into the empty stable `runtime/output` location while writers are stopped. When the filesystems differ, use an explicitly verified copy-and-cutover procedure and retire the original as a writable workspace. Historical records may include original absolute paths. Keep the provenance and audit bytes intact. Keep development writers on synthetic state after migration.
5. Put the reviewed active policy in `runtime/config/scope.json` with mode `0600`, replacing it with a complete sibling file by rename. Keep sensitive exports in a private directory outside the release source. Use absolute physical paths for `h1_snapshot_dir` and `burp_scope_file`. A comparison policy and its referenced sources belong under `runtime/config/policies`. Revalidate using `("$py" -E -s -B -m recon.scope_cli validate --config config/scope.json)` from the physical runtime directory, then review the fingerprint and campaign binding. Changes in fingerprints pause campaign network work as documented in the [scope guide](scope-authorization.md).
6. To roll back, stop clients and invoke `"$base" -I -S -B "$guard" activate "$root" "$previous_version" "$previous_manifest_sha256"`, then run `verify` and the offline checks. Use a previously sealed, reviewed version that is compatible with the current policy and campaign data. The 0.1.0 runtime was outside this rollback qualification. To retire the deployment, detach clients and preserve the private `runtime/config` and `runtime/output` and their verified backup before removing any versioned code.
